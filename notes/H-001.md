# H-001: Extend j*(l) past l=20 and characterize e(l) growth

Status: in-progress. Opened 2026-07-22.

## Implementation progress (2026-07-22)

Rust reimplementation at `experiments/E-001-jstar-fast/` (native `Vec<u64>` bitset with cyclic
rotation, same algorithm as `experiment_wcc.py`, parallelized with rayon across the independent
per-c updates within each exponent step). Validated against the l=1..7 reference table and the
l=2,j=2 pointwise check; reproduced l=1..18 exactly matching the known table.

**Cross-check caught a real bug (exactly what the honesty rules are for)**: the independent
brute-force cross-check (`src/bin/bruteforce.rs`, direct enumeration of R_{j-1,j}, no reduction,
no bitset/rotation) initially disagreed with the fast implementation for l=2,3,4 (found j*=3,4,5
instead of the expected 4,6,7). Investigated per Rule 8c/honesty rule 3 rather than assuming the
fast method was right: the bug was in the brute-force's own recursion (missing a lower-bound
check on intermediate exponents, an off-by-one in the "leave enough room for remaining strictly
smaller values" condition), not in the fast implementation. Confirmed independently with a small
Python script using `itertools.combinations` before touching the Rust code, then fixed the Rust
brute-force's bound check; both methods now agree exactly for l=1..4. This is the intended
outcome of requiring an independent cross-check: it can also catch a bug in the checker itself,
which is exactly why the checker needs to be a genuinely different method, not just a second
copy of the same logic.

Single-threaded run showed cost growing faster than Python's ~3.3x/step (closer to ~5x/step
observed l=16->17->18); adding rayon parallelism across the per-c updates (independent
read-state[c]/write-state[c+1] pairs within each exponent step, safe with no aliasing) brought
this back down toward ~3.6x/step and roughly halved wall-clock time at l=17-18.

## Benchmark at l=21-23 (2026-07-22): time was never the real constraint, memory is

Full run l=1..20 completed and matches the known table exactly, with real per-step timing:

```
l=17  j*=21  time=  6.406s
l=18  j*=22  time= 22.828s
l=19  j*=23  time= 78.022s
l=20  j*=24  time=271.156s  (cumulative 381.1s = 6.35 min, vs Python's ~2221s for l=18-20 alone)
```

Growth factor per step (~3.4-3.6x) is close to Python's ~3.3x/step, as expected: the fundamental
O(3^l) scaling is the same, native code and parallelism only give a constant-factor speedup
(here, roughly 6-9x depending on how the comparison is drawn). This alone already lands well
inside the "1 week of wall-clock" budget for several more l's on time grounds.

**But an initial, wrong estimate of the memory ceiling almost caused an OOM.** My first pass
(before running anything) computed "one bitset of 3^l bits" as the size to watch (e.g. 3^24 ~=
35.3GB, "fits in 62GB") and concluded l=25-28 was reachable. This missed that `state` in the DP
is a `Vec` of `l+1` FULL bitsets, all live simultaneously throughout the whole v-loop (the
knapsack structure needs every count-level, not just the final one), and that the rayon
parallel-collect phase holds roughly another `l` full bitsets transiently before merging. Real
resident memory is order `(l+1)*3^l/8` bytes for `state` alone, roughly doubling to
`~2*(l+1)*3^l/8` at peak during the parallel merge - not `3^l/8`. This was caught by the advisor
(consulted per Rule 11b before letting a long background run continue unsupervised) BEFORE it
turned into an uncontrolled OOM, by re-deriving the memory formula against what a Chapter's DP
structure actually holds live, not just the final answer's size.

Confirmed empirically (measured via `/proc/<pid>/status` while the l=21 computation was live,
not just computed on paper, per this project's honesty rule 4): RSS climbed to ~39GB and rising
partway through l=21 (predicted state-alone size 22*3^21/8 ~= 27.4GB, consistent with observed
RSS once transient rayon buffers are added), with only ~11GB "available" left on a 62GB machine
and swap already growing. The run was killed deliberately (SIGTERM, clean exit) before it could
either thrash the whole machine into heavy swapping or get OOM-killed uncontrolled.

**Corrected projection**:
```
l=20: state ~=  8.7 GiB  (21 * 3^20 / 8)   -- completed, fits comfortably
l=21: state ~= 27.4 GiB  (22 * 3^21 / 8)   -- peak (with transients) ~50-55 GiB, marginal on 62GB
l=22: state ~= 84.0 GiB  (23 * 3^22 / 8)   -- exceeds 62GB outright, not reachable on this machine
l=23: state ~= 271  GiB                    -- not reachable
```
This directly contradicts the brief's "meta realista: l=25-28", which was extrapolated from
Python's wall-clock cost alone and did not account for the `(l+1)` memory factor being intrinsic
to the count-indexed knapsack DP (not an artifact of Python vs. Rust, or of this particular
implementation's parallelism choice: any implementation holding the full triangular DP table
faces the same `Theta((l+1)*3^l)` memory wall). Packing only the non-multiples-of-3 residues
(the ~33% saving considered in the technical guide) would buy at most a fraction of one extra
level, not several.

**Safety fix applied**: added `debug_assert!(j >= ell)` in `image_size` (the reduction
`R_{j-1,j} = 2^{j-l}*R_{l-1,j}` requires j>=l; since e(l) is o(l), j*(l) < l becomes possible only
around l~38+, unreachable at this implementation's actual ceiling of l~20-21, but a one-line
guard against a silent-wrong-answer trap costs nothing).

## Definição do objeto matemático

Para inteiros j, k >= 0, defina o conjunto de inteiros 3-ádicos:

```
R_{j,k} := { sum_{i=0}^{j} 2^{alpha_i} 3^i  :  j+k >= alpha_0 > alpha_1 > ... > alpha_j >= 0 }  subset Z*_3
```

Somas de j+1 potências de 2 multiplicadas por potências de 3 crescentes, com expoentes de 2
estritamente decrescentes e limitados por j+k. O tamanho deste conjunto é exatamente
`C(j+k+1, j+1)` (coeficiente binomial), mas o tamanho da sua imagem módulo 3^l (quantos resíduos
distintos em (Z/3^lZ)* ele cobre) é o que importa.

**Cobertura**: R_{j,k} "cobre" Z*_3 mod 3^l se a imagem de R_{j,k} módulo 3^l contém todas as
`2*3^{l-1}` classes de resíduo invertíveis módulo 3^l.

**Definição central**: `j*(l)` = o menor j tal que `R_{j-1,j}` cobre Z*_3 mod 3^l.

## A conjectura (Wirsching 1998, Weak Covering Conjecture, Conjectura 3.9)

Existe uma função sub-exponencial K(l) > 0 (isto é, `lim_l K(l)*e^{-gamma*l} = 0` para todo
gamma > 0) tal que, para todo j, l: se `|R_{j-1,j}| >= K(l)*3^l` então `R_{j-1,j}` cobre Z*_3
mod 3^l.

Essa conjectura é equivalente (identidade algébrica provada, não analogia) à conjectura beta=1
de Terence Tao (2020) sobre densidade de pré-imagens de Collatz, e implica densidade positiva de
predecessores no problema de Collatz, um dos passos mais importantes rumo à conjectura completa.

futuro (Rule 11 pede checagem bibliográfica antes de ir para uma bibliografia formal).

Algoritmo original (a reimplementar de forma mais rápida, não copiar em Python):

```
Para cada l, buscar o menor j tal que R_{j-1,j} cobre Z/3^lZ:
  - Processar expoentes candidatos em ordem decrescente
  - Manter, para cada contagem c de termos já escolhidos, o conjunto de somas parciais
    alcançáveis mod 3^l como um bitset
  - Escolher o expoente v na posição c é uma ROTAÇÃO CÍCLICA do bitset por 2^v * 3^c mod 3^l
  - Contagem de bits do bitset final = tamanho da imagem (cobertura)
```

Redução útil já identificada (usar para cortar custo): para j >= l, termos de índice i >= l se
anulam mod 3^l, dando `R_{j-1,j} mod 3^l = 2^{j-l} * R_{l-1,j} mod 3^l`, que reduz o custo de
enumeração de `C(2j,j)` para `C(j+l,l)`.

## Memory optimization and l=21 success (2026-07-22)

After the critique pass, the researcher asked a direct question: would l=21 alone (not batched)
actually fit? Re-examining the near-OOM from the earlier attempt: peak memory wasn't really
`~2*(l+1)*3^l/8` as an unavoidable cost, it was an avoidable inefficiency in how the parallelism
was implemented. The previous version computed all `ell` rotated bitsets for a given exponent
step in parallel, collected them into a `Vec`, then merged - holding up to `ell` extra full-size
bitsets alongside the `l+1`-bitset `state` array at once. Rewrote this: reverted the outer loop
over count-index `c` to sequential, decreasing order (matching the original single-threaded
algorithm's own correctness argument exactly, no "snapshot" trick needed), and moved parallelism
*inside* each individual rotate/shift/OR operation instead (splitting the word array into chunks
via rayon; each output word depends on at most two fixed input words, so this has no
inter-thread dependency and needs no synchronization). This keeps only one extra full-size
temporary bitset alive at a time (the current rotation being computed), not `ell` of them,
bringing peak memory down to roughly `(l+2)*3^l/8` bytes instead of `~2*(l+1)*3^l/8`: about
28-30 GiB for l=21 instead of ~50-55 GiB.

Re-validated (both `cargo build` and `cargo build --release`, `validate`, `bruteforce`, and a
re-run of l=1..20, which came out ~27% faster than the previous parallelization strategy as a
side benefit: l=20 in 198.1s vs. 271.2s before). Also caught and fixed, before running l=21 for
real, a comment that inaccurately claimed "only one extra temporary" when the code actually held
two (`shl` and `shr` results) simultaneously; changed the code (not just the comment) to
apply the `shl` result and drop it before computing the `shr` result, making the claim literally
true rather than just adjusting the words.

**Ran l=21 alone with a watchdog tracking both process RSS and system-wide available memory**
(the second watchdog explicitly checks `MemAvailable` from `/proc/meminfo`, not just the
process's own RSS, after the earlier near-miss showed system-wide headroom is what actually
matters). Memory oscillated between ~2GiB and ~28GiB repeatedly (each oscillation is one `j`
attempt in `find_j_star`'s scan from `j=21` upward: `state` is freed when a non-covering attempt
returns, then reallocated for the next `j`), never approaching the 43GiB per-process or 4GiB
system-available thresholds. Total wall time across all attempts: 748.1s (~12.5 min).

**Result: j\*(21) = 25.** e(21) = 8.358 (a new maximum in the series, exceeding e(20)=8.150),
j\*(21)/21 = 1.1905 (continuing the decreasing trend). This is the first genuinely new data
point beyond the previous paper's l=1..20 table. No independent cross-check exists at l=21
itself (the brute-force method is only tractable to l<=4); confidence rests on the same,
unchanged, already-doubly-validated algorithm and code path that reproduced l=1..20 exactly.

**l=22 remains out of reach, full stop.** Its state array alone needs ~86GiB regardless of any
in-place/transient optimization (the optimization removed the *transient* doubling, not the base
`(l+1)*3^l/8` cost of holding the DP table itself, which is intrinsic to this algorithm's
structure). This is not a matter of further engineering effort on this same approach; a
fundamentally different, sub-`3^l`-memory algorithm would be needed, which remains a separate,
unpursued research question (see the report's open-items section).

The e(l) statistical comparison (E-002) was rerun with l=21 folded in (tail now l=10..21, n=12):
the qualitative finding **strengthens** with the new point (ΔAIC against stabilization rises from
5.04 to 8.07; plateau-test p drops from 0.075 to 0.062, still short of 0.05). Full numbers in

## Reconsidering l=22: the invertible-residue packing may be more than "a fraction of a level"

After l=21 succeeded, the researcher asked directly whether l=22 might now be reachable. My
earlier assessment (and the advisor's, in the same conversation) dismissed the "pack only
non-multiples-of-3" optimization from the original technical guide as buying "at most a fraction
of one additional level" - that was a rough, size-only heuristic (2/3 of 3^l is still the same
order of magnitude as 3^l) that did not actually check whether the resulting total fits under
62GB for l=22 specifically. Redone carefully:

**The packing is mathematically valid, not just a size heuristic.** For c>=1, state[c] contains
only residues invertible mod 3 (the first chosen exponent always lands on position 0, contributing
a non-multiple-of-3 term; every other position contributes a multiple of 3). Writing an invertible
residue as r=3k+s with s in {1,2}, k in [0,3^(l-1)), addition by any multiple of 3 (which is what
every transition c -> c+1 for c>=1 does, since the offset 2^v*3^c is itself divisible by 3 once
c>=1) only changes k (cyclically mod 3^(l-1)) and never s. So each state[c] (c=1..l) can be
represented as TWO independent bitsets of size 3^(l-1) (one per class s=1,2) instead of one dense
bitset of size 3^l, and the DP's rotation-based updates remain simple cyclic rotations, just on a
ring of size 3^(l-1) instead of 3^l, applied to each of the two sub-bitsets separately. Checked
by hand against l=2 (mod 9: classes {1,4,7} and {2,5,8}, k in {0,1,2} each, addition by 6=3*2
maps k=0 (r=1) to k=2 (r=7), matching 1+6=7 directly).

**Redone memory arithmetic for l=22 specifically** (not just "2/3 of a huge number, still huge"):
state array (c=1..22, 2 sub-bitsets of 3^21 bits each per level, state[0] trivial) needs
`22 * 2 * 3^21/8` bytes ~= 53.6 GiB, versus ~84.0 GiB for the current dense representation. Adding
one transient sub-bitset-pair (the in-flight rotation, matching the l=21 fix's single-temporary
design) brings peak to roughly 56 GiB - inside the 62GB machine, but only barely (about 90% of
total RAM, right at Rule 9b's own suggested ceiling, and tighter than l=21's ~28GiB peak that
came in well under budget). This is a real, moderate engineering effort (rewriting `image_size`'s
bitset representation, not a research-risk sub-exponential algorithm), but it is genuinely tight,
not a comfortable margin, and l=23 would still need ~3x more even with this packing (~168GB), so
this would at most reach exactly one further level (l=22), not reopen the extension indefinitely.
**Decisive check (advisor consultation, 2026-07-22): l=22 does not fit even with this packing,
and the reason is the exact blind spot that nearly caused the earlier OOM.** The 53.6 GiB packed
state array must be fully resident throughout (the `(l+1)`-level dimension is intrinsic; packing
only removes the 1/3 factor, not the count-level dimension) - that is a fixed floor, not a peak
that comes and goes. Using this session's own measured numbers from the successful l=21 run
(process RSS ~26.8 GiB against `MemAvailable` ~27.0 GiB out of 62 GiB total), non-process system
overhead is ~8 GiB and will still be there at l=22. `53.6 (resident state) + 8 (measured
overhead) ~= 61.6 GiB`, before a single transient rotation buffer (another 1-2 GiB) is even
computed - already at the 62GB ceiling with zero headroom, on a machine whose swap is only 8GiB.
This is the same "per-process number looks fine, system-wide is what actually bites" pattern as
the first l=21 near-miss, just not caught until asked to re-check with this session's own
measured overhead instead of a fresh isolated estimate.

**[SUPERSEDED] Conclusion (as it stood before the swap expansion): l=22 needs a bigger-RAM
machine, not a better implementation.** This assumed the only paths forward were "fits in
physical RAM" or "not reachable at all", and did not consider swap as a legitimate option given
this project's original framing (the memory-optimization work up to this point was entirely about
staying inside physical RAM, never about accepting swap I/O as the cost of reaching a level). The
researcher's decision to add 500GiB of swap specifically for this purpose reopened the question;
see the next section for what actually happened.

## l=22 reached via swap, and l=23 attempted the same way (2026-07-22)

The researcher added a 500GiB swap file to this machine (replacing the original 8GiB swap) after
the packed-representation analysis above showed l=22's memory floor (~61.6GiB) was only barely
above physical RAM (62GiB), specifically to test whether swap could bridge that gap despite the
random-access, memory-bandwidth-heavy access pattern of the bitset rotation DP (a pattern where
swap is normally expected to be prohibitively slow, since each rotation touches the whole state
array, not a small hot working set).

**First attempt (unmodified dense representation, no packing) was accidentally killed** by a
`systemd` session restart unrelated to this computation (the researcher killed the wrong process
during an interactive session and the machine restarted the desktop session, which SIGKILLed
every process in the user's session, including this one, per `journalctl`). Not a memory failure;
confirmed via `journalctl -k` showing `page allocation failure` warnings around the time of the
session restart, consistent with heavy swap pressure but not an OOM kill of this specific process.

**Second attempt succeeded**: `jstar-fast run 22 22`, run via `setsid nohup` (to survive terminal/
session disruptions) with two watchdogs in sequence tracking both process RSS and system-wide
`MemAvailable`. Memory oscillated between roughly 2 GiB and 84 GiB repeatedly across several `j`
attempts before finding the covering one (`find_j_star` scans `j` upward from `l`, freeing and
reallocating `state` between non-covering attempts), swap usage plateauing near 83-84 GiB during
each attempt's steady-state phase, matching the dense-representation prediction almost exactly.
System-wide available memory dropped as low as ~0.1-0.3 GiB repeatedly but never fully exhausted;
no repeat of the near-crash pattern from the first l=21 attempt. Total wall time: 10749.3s
(~2h59m), roughly 14x l=21's 748.1s despite the state array being only ~3.1x larger, consistent
with swap I/O (not compute) being the dominant cost once the state exceeds physical RAM.

**Result: j\*(22) = 26.** e(22) = 8.565 (a new maximum, exceeding e(21)=8.358), j\*(22)/22 =
1.1818 (continuing the decreasing trend). This is a second genuinely new data point beyond both
the previous paper's table and H-001's earlier l=21 result. As with l=21, no independent
cross-check exists at l=22 itself; confidence rests on the same, unchanged, already-doubly-
validated algorithm and code path, now also empirically consistent (memory usage matched the
dense-representation prediction closely, a form of internal consistency check even without an
independent second method).

**l=23 attempted next** (same approach, same watchdog pattern), per the researcher's explicit
request after l=22's success, aware this would need roughly 3x more state (~263GiB) and could take
substantially longer than l=22's ~3 hours given the swap-I/O-bound scaling observed. See the
Status section below for its outcome once complete; this note will be updated when it finishes
either way (success, or the researcher electing to stop it).

**On the swap-capacity question specifically**: 500GiB was chosen generously, not calculated
precisely; the actual requirement for l=22 turned out to be ~84GiB (matching the dense-
representation theoretical figure closely), and l=23 would need roughly 263GiB, both comfortably
under 500GiB. No swap resizing was needed between l=22 and l=23.
