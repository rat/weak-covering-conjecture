Status: in-progress. Opened 2026-07-22.

## Implementation progress (2026-07-22)

Rust reimplementation at `experiments/E-001-jstar-fast/` (native `Vec<u64>` bitset with cyclic
rotation, same algorithm as `experiment_wcc.py`, parallelized with rayon across the independent
per-c updates within each exponent step). Validated against the l=1..7 reference table and the
l=2,j=2 pointwise check; reproduced l=1..18 exactly matching the known table.

**Cross-check caught a real bug (exactly what the honesty rules are for)**: the independent
brute-force cross-check (`src/bin/bruteforce.rs`, direct enumeration of R_{j-1,j}, no reduction,
no bitset/rotation) initially disagreed with the fast implementation for l=2,3,4 (found j*=3,4,5
instead of the expected 4,6,7). Investigated per Rule 8c/honesty rule 3 rather than assuming the
fast method was right: the bug was in the brute-force's own recursion (missing a lower-bound
check on intermediate exponents, an off-by-one in the "leave enough room for remaining strictly
smaller values" condition), not in the fast implementation. Confirmed independently with a small
Python script using `itertools.combinations` before touching the Rust code, then fixed the Rust
brute-force's bound check; both methods now agree exactly for l=1..4. This is the intended
outcome of requiring an independent cross-check: it can also catch a bug in the checker itself,
which is exactly why the checker needs to be a genuinely different method, not just a second
copy of the same logic.

Single-threaded run showed cost growing faster than Python's ~3.3x/step (closer to ~5x/step
observed l=16->17->18); adding rayon parallelism across the per-c updates (independent
read-state[c]/write-state[c+1] pairs within each exponent step, safe with no aliasing) brought
this back down toward ~3.6x/step and roughly halved wall-clock time at l=17-18.

## Benchmark at l=21-23 (2026-07-22): time was never the real constraint, memory is

Full run l=1..20 completed and matches the known table exactly, with real per-step timing:

```
l=17  j*=21  time=  6.406s
l=18  j*=22  time= 22.828s
l=19  j*=23  time= 78.022s
l=20  j*=24  time=271.156s  (cumulative 381.1s = 6.35 min, vs Python's ~2221s for l=18-20 alone)
```

Growth factor per step (~3.4-3.6x) is close to Python's ~3.3x/step, as expected: the fundamental
O(3^l) scaling is the same, native code and parallelism only give a constant-factor speedup
(here, roughly 6-9x depending on how the comparison is drawn). This alone already lands well
inside the "1 week of wall-clock" budget for several more l's on time grounds.

**But an initial, wrong estimate of the memory ceiling almost caused an OOM.** My first pass
(before running anything) computed "one bitset of 3^l bits" as the size to watch (e.g. 3^24 ~=
35.3GB, "fits in 62GB") and concluded l=25-28 was reachable. This missed that `state` in the DP
is a `Vec` of `l+1` FULL bitsets, all live simultaneously throughout the whole v-loop (the
knapsack structure needs every count-level, not just the final one), and that the rayon
parallel-collect phase holds roughly another `l` full bitsets transiently before merging. Real
resident memory is order `(l+1)*3^l/8` bytes for `state` alone, roughly doubling to
`~2*(l+1)*3^l/8` at peak during the parallel merge - not `3^l/8`. This was caught by the advisor
(consulted per Rule 11b before letting a long background run continue unsupervised) BEFORE it
turned into an uncontrolled OOM, by re-deriving the memory formula against what a Chapter's DP
structure actually holds live, not just the final answer's size.

Confirmed empirically (measured via `/proc/<pid>/status` while the l=21 computation was live,
not just computed on paper, per this project's honesty rule 4): RSS climbed to ~39GB and rising
partway through l=21 (predicted state-alone size 22*3^21/8 ~= 27.4GB, consistent with observed
RSS once transient rayon buffers are added), with only ~11GB "available" left on a 62GB machine
and swap already growing. The run was killed deliberately (SIGTERM, clean exit) before it could
either thrash the whole machine into heavy swapping or get OOM-killed uncontrolled.

**Corrected projection**:
```
l=20: state ~=  8.7 GiB  (21 * 3^20 / 8)   -- completed, fits comfortably
l=21: state ~= 27.4 GiB  (22 * 3^21 / 8)   -- peak (with transients) ~50-55 GiB, marginal on 62GB
l=22: state ~= 86.1 GiB  (23 * 3^22 / 8)   -- exceeds 62GB outright, not reachable on this machine
l=23: state ~= 271  GiB                    -- not reachable
```
This directly contradicts the brief's "meta realista: l=25-28", which was extrapolated from
Python's wall-clock cost alone and did not account for the `(l+1)` memory factor being intrinsic
to the count-indexed knapsack DP (not an artifact of Python vs. Rust, or of this particular
implementation's parallelism choice: any implementation holding the full triangular DP table
faces the same `Theta((l+1)*3^l)` memory wall). Packing only the non-multiples-of-3 residues
(the ~33% saving considered in the technical guide) would buy at most a fraction of one extra
level, not several.

**Safety fix applied**: added `debug_assert!(j >= ell)` in `image_size` (the reduction
`R_{j-1,j} = 2^{j-l}*R_{l-1,j}` requires j>=l; since e(l) is o(l), j*(l) < l becomes possible only
around l~38+, unreachable at this implementation's actual ceiling of l~20-21, but a one-line
guard against a silent-wrong-answer trap costs nothing).

**Where this leaves H-001's checklist**: l=20 reproduced and confirmed (matches H-114 exactly);
l=21 is new data, technically reachable but memory-marginal on this 62GB machine (would need
careful supervision, or the ~33% non-multiple-of-3 packing optimization first to have real
headroom); l=22+ is not reachable with the dense bitset approach on this hardware, full stop.
This is a legitimate instance of the checklist's own "condição de parada válida" (stopping when
projected cost exceeds a reasonable budget), just triggered by memory rather than time, and much
earlier than the brief anticipated. Options going forward (not yet decided, pending the
researcher): (a) attempt l=21 carefully with memory monitoring, possibly after the non-multiple-
of-3 packing optimization for headroom; (b) accept l<=20 (already an extension of zero, since
the existing table already had l=1..20) or l=21 as the practical ceiling for this line of attack
and move to Part B (explicitly framed by the researcher's own checklist as a valid, successful
outcome, not a failure); (c) invest in a fundamentally different, sub-`3^l`-memory algorithm,
which is a real research question with no guaranteed payoff, not an engineering afterthought.

## Definição do objeto matemático

Para inteiros j, k >= 0, defina o conjunto de inteiros 3-ádicos:

```
R_{j,k} := { sum_{i=0}^{j} 2^{alpha_i} 3^i  :  j+k >= alpha_0 > alpha_1 > ... > alpha_j >= 0 }  subset Z*_3
```

Somas de j+1 potências de 2 multiplicadas por potências de 3 crescentes, com expoentes de 2
estritamente decrescentes e limitados por j+k. O tamanho deste conjunto é exatamente
`C(j+k+1, j+1)` (coeficiente binomial), mas o tamanho da sua imagem módulo 3^l (quantos resíduos
distintos em (Z/3^lZ)* ele cobre) é o que importa.

**Cobertura**: R_{j,k} "cobre" Z*_3 mod 3^l se a imagem de R_{j,k} módulo 3^l contém todas as
`2*3^{l-1}` classes de resíduo invertíveis módulo 3^l.

**Definição central**: `j*(l)` = o menor j tal que `R_{j-1,j}` cobre Z*_3 mod 3^l.

## A conjectura (Wirsching 1998, Weak Covering Conjecture, Conjectura 3.9)

Existe uma função sub-exponencial K(l) > 0 (isto é, `lim_l K(l)*e^{-gamma*l} = 0` para todo
gamma > 0) tal que, para todo j, l: se `|R_{j-1,j}| >= K(l)*3^l` então `R_{j-1,j}` cobre Z*_3
mod 3^l.

Essa conjectura é equivalente (identidade algébrica provada, não analogia) à conjectura beta=1
de Terence Tao (2020) sobre densidade de pré-imagens de Collatz, e implica densidade positiva de
predecessores no problema de Collatz, um dos passos mais importantes rumo à conjectura completa.

Achado adicional (2026-07-22, verificado diretamente contra o PDF do livro via pdftotext, não

e em H-114 do projeto anterior não bate com a numeração exata da fonte primária, que rotula a
definição de R_{j,k} como "Corollary & Notation 1.8" dentro do Capítulo V, Seção 1 (p.127); o
número de página está correto nas duas. Não é um problema de conteúdo matemático, só um rótulo
de referência cruzada interno; registrado aqui para não repetir a citação errada num paper
futuro (Rule 11 pede checagem bibliográfica antes de ir para uma bibliografia formal).

Algoritmo original (a reimplementar de forma mais rápida, não copiar em Python):

```
Para cada l, buscar o menor j tal que R_{j-1,j} cobre Z/3^lZ:
  - Processar expoentes candidatos em ordem decrescente
  - Manter, para cada contagem c de termos já escolhidos, o conjunto de somas parciais
    alcançáveis mod 3^l como um bitset
  - Escolher o expoente v na posição c é uma ROTAÇÃO CÍCLICA do bitset por 2^v * 3^c mod 3^l
  - Contagem de bits do bitset final = tamanho da imagem (cobertura)
```

Redução útil já identificada (usar para cortar custo): para j >= l, termos de índice i >= l se
anulam mod 3^l, dando `R_{j-1,j} mod 3^l = 2^{j-l} * R_{l-1,j} mod 3^l`, que reduz o custo de
enumeração de `C(2j,j)` para `C(j+l,l)`.

## Guia técnico inicial

1. Reimplementar em Rust ou C++ usando bitsets nativos (`std::bitset`/`Vec<u64>` com popcount,
   ou GMP se precisar de módulos maiores). Operação central: `bitset_novo = bitset_antigo
   ROTACIONADO por (2^v * 3^c mod 3^l) bits, depois OR com o bitset acumulado`.
2. Paralelismo: considerar múltiplos núcleos (16 disponíveis, ver Section 1 do CLAUDE.md).
   GPU/CUDA não disponível nesta máquina (só gráfico integrado Intel); descartar essa via.
3. Usar a redução já conhecida: `R_{j-1,j} mod 3^l = 2^{j-l}*R_{l-1,j} mod 3^l` para j >= l.
4. Busca de j*(l) por bisseção (cobertura é monótona em j), não varredura linear.
